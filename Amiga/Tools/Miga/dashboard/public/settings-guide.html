Miga Settings Guide

This page explains what each saved setting changes, why it exists, and when you would actually use it. If you want to edit the saved values instead of reading about them, open the live Settings editor. Return to the live dashboard

1. Profiles

  • Active Profile: chooses which saved bundle of settings the dashboard and terminal tools use by default. Use this when you switch between repeatable workflows such as benchmark runs, corpus validation, or an LM Studio-backed mutation setup.
  • Create Profile From Current: saves the values currently shown in the editor into a new named profile. Use this when you have a working combination you want to reuse later without retyping every field.
  • Delete Active Profile: removes a non-default profile. Use this when an old experiment preset is no longer useful and you do not want it cluttering the selector.

2. Dashboard Defaults

  • Iterations: pre-fills how many runs a queued batch should execute. Keep this at 1 while debugging; raise it when you want unattended repeated runs.
  • Seed: pre-fills the source-selection seed. Use a fixed seed when you want the selection path to be reproducible.
  • Run Method: chooses the default workflow the monitor opens with. Use corpus_validation for runnable-source checks, copper_reference for control runs, and copper_mutation for the real optimization path.
  • Kick ROM: preselects the ROM file used when queueing runs. Set this when you are repeatedly comparing against one exact ROM instead of switching manually each time.
  • Source Filter: narrows auto-selection to manifest rows containing the typed text. Use this when you want a profile dedicated to one corpus family or subfolder.
  • Manifest Index: pins one exact manifest row when non-zero. Use this for repeatable investigations of one source file.
  • Auto-select Source: decides whether the monitor picks a source before every run. Turn it off only when you want to keep the current workspace source fixed between iterations.
  • Allow Include Files: lets the selector pull in include/header-like files. Use this only when you intentionally want fragments in the candidate pool.
  • Allow Non-entrypoint Files: allows files that do not look like standalone programs. Use this only for broader corpus mining or debugging unusual cases.

3. Benchmark Defaults

  • Kick ROM Name: default ROM name for the source benchmark evaluator when terminal tools do not override it. Use this when you want CLI benchmark runs to follow one ROM choice by default.
  • ROM Directory: where benchmark tools look for ROM files. Change this only if your ROMs live somewhere other than the repo's normal roms/ location.

4. Mutation Loop Defaults

  • Iterations: how many mutation attempts the loop should run. Use small numbers while testing a mutator; use larger numbers for unattended exploration.
  • Seed: reproducibility control for mutation candidate generation. Use a fixed seed if you want to compare two loop runs more directly.
  • Mutator: chooses how candidates are selected, such as heuristic, openai, or lmstudio. Pick this based on whether you want local heuristics, hosted OpenAI calls, or a local LM Studio server.
  • Mutation Strategy: constrains which edit type the loop may propose. Use this when debugging one operator, such as only shifting Copper pairs or only removing them.
  • Candidate Budget: limits how many candidates are generated before the chooser picks one. Raise it when you want broader search; lower it when you want faster and simpler runs.
  • Benchmark Config: points to the JSON config for the source-built benchmark. Change this only when you are moving to a different benchmark task or config file.
  • Eval Script: selects the evaluator entry point used by the mutation loop. Keep the default unless you are deliberately swapping in another evaluator.
  • Loop Directory: output folder for mutation-loop logs, results, and archived runs. Use a custom path when you want to separate one campaign from another; otherwise keep the repo default.
  • Results File: optional explicit TSV path instead of the default file inside the loop directory. Use this when you want multiple loops to write into separate named result logs.

5. OpenAI Defaults

  • Model: default model name for the OpenAI-backed mutator. Change this when you are comparing response quality, cost, or reasoning behavior.
  • Reasoning Effort: default effort level for supported reasoning models. Raise it when the model needs more deliberate candidate choice; lower it when speed matters more.
  • API Key Environment Variable: the env var name the loop should read for the OpenAI API key. Change this only if your shell uses a nonstandard variable name.
  • Base URL: the endpoint used for OpenAI-compatible requests. Keep the default unless you are targeting a compatible gateway or proxy.

6. LM Studio Defaults

  • Base URL: where the loop should reach the LM Studio server. Change it when LM Studio is on a different host or port.
  • Model: optional LM Studio model identifier. Use this when the server exposes multiple local models and you want one pinned in the saved profile.
  • Token Environment Variable: optional env var name for an auth token if your local gateway requires one. Most local setups can leave this alone.

7. Terminal Preview

The preview shows the command implied by the currently edited mutation-loop settings. Its purpose is auditability: you can see the exact flags the saved defaults would feed into amiga_copper_mutation_loop.py before running anything.

Use the preview when you want to sanity-check a profile quickly, especially after changing mutator, benchmark config, or loop directory values.

8. Practical Scenarios

Scenario: Copper work

  • Objective: iterate on Copper-list behavior or the source-built Copper benchmark.
  • Explanation: this is the main mutation-loop path in the repo. You want the dashboard and loop defaults aimed at the mutable Copper benchmark, not at corpus validation or the fixed reference disk.
  • Recommended settings: set Run Method to copper_mutation, keep Auto-select Source off when you are intentionally editing the fixed mutation workspace, keep Benchmark Config pointed at amiga_workspace/benchmarks/copper_bars/source_benchmark.json, keep Eval Script on amiga_eval_benchmark_source.py, and use a dedicated Loop Directory if you want one Copper campaign separated from another.

Scenario: Fixed-source corpus investigation

  • Objective: repeatedly test one exact runnable source from the corpus without random source churn.
  • Explanation: this is where the dashboard defaults matter a lot. You want the monitor to open in corpus validation mode but already pinned to one source-selection path instead of picking a new candidate every time.
  • Recommended settings: set Run Method to corpus_validation, turn Auto-select Source off if you are keeping a copied source in the workspace, or keep it on with a nonzero Manifest Index when you want one exact manifest row. Use Source Filter only if you want the profile narrowed to one corpus family, and set a fixed Kick ROM when ROM differences are part of the investigation.

Scenario: LM Studio mutation profile

  • Objective: run the mutation loop against a local LM Studio server instead of the heuristic chooser or hosted OpenAI.
  • Explanation: this is a profile-driven setup. The saved settings define which mutator backend is used, where the local server lives, and which optional local model ID should be pinned.
  • Recommended settings: set Mutator to lmstudio, set LM Studio Base URL to the host and port your local server exposes, optionally fill LM Studio Model if you want one model pinned, and keep the usual Copper mutation defaults for Run Method, Benchmark Config, and Eval Script. Save this as its own profile so you can switch between local and hosted mutators without rewriting fields.
