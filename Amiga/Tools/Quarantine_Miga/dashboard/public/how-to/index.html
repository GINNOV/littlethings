Miga Dashboard Guide

1. Start The Dashboard

  1. Open Terminal in the project root.
  2. Run:
npm run monitor:start
  1. Open http://localhost:4173.

Default access is local-only (127.0.0.1).

2. Optional Token Protection

Use token protection when you want the dashboard to stay viewable, but you do not want other people or browser tabs to be able to queue runs or clear the queue without permission.

This matters most if you expose the monitor beyond your own local session.

Launch with a token:

MONITOR_API_TOKEN='change-me' npm run monitor:start

Then open:

http://localhost:4173/?token=change-me

The token is only required for run-control actions such as queueing and clearing jobs.

3. Status Strip

The pills at the top give the fastest summary of what the monitor is doing right now.

  • State: whether the runner is currently idle or executing a batch.
  • Iteration: the current position inside the active batch, such as 4/100.
  • Pending: how many iterations are still left to run, including the rest of the current batch.
  • Time: the browser's current local time, useful when checking whether the page is still refreshing.

4. Kick Off Runs

This is the control panel for starting a batch. Use it when you want to test new sources, compare ROMs, or switch between validation and benchmark workflows.

  • Iterations: how many runs to execute in this batch.
  • Seed: changes deterministic source selection when random picking is enabled.
  • Source Filter: narrows auto-selection to manifest rows whose paths contain the text you type.
  • Manifest Index: pins one exact manifest row instead of letting auto-select choose randomly. This is useful for repeatable runs, debugging one exact source, and comparing the same source across ROMs or run methods. Use 0 to disable it.
  • Kick ROM: selects which ROM file to use for this batch.
  • Run Method: choose the exact evaluator path the dashboard should launch, from corpus validation through fixed, suite, and setup-sensitive benchmarks.
  • Auto-select source before each run: pick a source automatically before every iteration. Turn this off only when you want to keep the current amiga_workspace/main.s unchanged.
  • Allow include files (.i/.inc): let selection include include/header-style files, not just normal .s or .asm sources.
  • Allow non-entrypoint files: let selection use files that do not look like standalone programs with a clear start label.
  • Queue Run Batch: adds the batch to the runner.
  • Clear Waiting Queue: removes waiting batches only. It does not stop the iteration that is already running.

5. Run Methods

Run Method changes which evaluator path the dashboard launches. Only Corpus validation uses source-selection controls. Every other method runs a fixed benchmark configuration directly.

  • Corpus validation: the dashboard builds the runnable manifest when needed, optionally auto-selects a corpus source, then runs the standard assemble, emulate, and verify flow.
  • Corpus validation: use this when the question is "does a corpus source still run correctly?" This is the only mode where Source Filter, Manifest Index, Seed, Auto-select source, Allow include files, and Allow non-entrypoint files matter.
  • Copper bars reference benchmark: runs the known-good Copper bars ADF against the original full-frame crop. Use it as the control path for ROM handling, emulator behavior, screenshot capture, and benchmark stability.
  • Copper bars assembly benchmark: builds the inline-assembly Copper bars workspace and scores it against the original full-frame crop. Use it when you want a single-task view of the current assembly workspace.
  • Copper bars suite benchmark: runs the inline-assembly suite, which combines the full-frame crop and the midband crop. Use it when you want the broader Copper-bars check instead of one crop only.
  • Playfield marker benchmark: builds the setup-sensitive playfield-marker source and scores a top-left crop where display-window and fetch setup visibly matter. Use it when you are testing non-Copper setup logic.
  • Playfield structure control: runs the intentionally wrong setup control against the same playfield-marker crop. Use it to confirm the setup-sensitive benchmark is still able to fail when setup constants are wrong.
  • Sin/Cos scroller benchmark: runs the glyph-based three-frame text scroller suite at `2s`, `4s`, and `6s`. Use it when you want the current benchmarked text-effect path instead of the Copper tasks.
  • Sin/Cos scroller control: runs the fixed-position text control against the same three-frame suite. Use it to confirm the scroller benchmark still fails when the motion is wrong.

6. Latest Report Snapshot

This card summarizes the most recent evaluator result. It is the quickest place to see whether the last run assembled, booted, and passed verification.

  • Score: the current normalized result from the evaluator.
  • Assemble: whether the source built into an executable.
  • Emulator: whether the emulator stage completed without a detected crash.
  • Verify: whether the deterministic verification stage passed. In benchmark modes this label changes to Benchmark.
  • Iterations Done: current batch progress while running, or final batch position after completion.
  • Selected Source / Kick ROM: the exact inputs used for the latest run.
  • Latest outcome: explains the difference between evaluator success and keep/discard status. For example, a benchmark can pass perfectly and still be marked discard when it only ties the current best score.

7. Live Run Log

This is the live terminal-style feed for the active iteration. Use it when a run looks stalled, fails unexpectedly, or you want to see which stage is running now.

  • Job / iteration header: identifies the active batch and position.
  • Phase: shows whether the runner is selecting, evaluating, or finishing.
  • Run tag: the unique ID for the archived run folder.
  • Log lines: streamed output from selection and evaluation commands.

8. Recent Archived Runs

This list is a quick audit trail of recent completed runs. Use it to compare sources, ROMs, and statuses without opening the filesystem directly.

  • Action: whether the loop kept, discarded, or crashed that run. This is separate from whether the evaluator passed.
  • Score: the stored score for that archived run.
  • Source / ROM: the exact source and ROM used in that run.

9. Score Trend

The chart shows how scores evolve over time. It is useful for spotting flatlines, regressions, and sudden improvements.

  • Each point is one recorded run.
  • Point color follows run status: keep, discard, or crash.
  • The summary above the chart shows run count, latest score, and best score in the current filtered view.
  • Terminal mutation-loop batches feed this chart too, so local LM Studio or heuristic runs appear alongside browser-queued runs.
  • If the chart is flat, the underlying runs are likely repeating the same source or mode and producing the same score.

10. History

This table combines dashboard-triggered runs with terminal mutation-loop runs. It is the best place to inspect a longer sequence of runs and filter down to a smaller slice.

  • Action Filter: show only keep, discard, or crash rows.
  • Today only: restrict the table to runs recorded today.
  • Run Method: shows which workflow produced the row, such as corpus validation, the Copper bars suite benchmark, or the playfield marker benchmark.
  • Result: shows whether the evaluator itself passed, independent of keep/discard. This makes it clear when a benchmark passed but was discarded only because it did not improve the current best score.
  • Description: includes the run tag, selected source, mode, and ROM for each row.
  • Screenshot: opens the archived image for that run when the evaluator saved one.

11. Typical Workflow

  1. Set Iterations (start with `1`).
  2. Choose a Kick ROM from the dropdown (or keep Auto).
  3. Choose a Run Method. Corpus validation is for strict runnable-corpus checks. Copper bars reference benchmark is the fixed control disk. Copper bars suite benchmark is the broader benchmark path for the inline-assembly workspace. Playfield marker benchmark checks display-window and fetch logic. Sin/Cos scroller benchmark is the current text-effect suite.
  4. Set Manifest Index to a positive number only if you want one exact manifest row. Leave it at `0` for normal selection behavior.
  5. Leave Auto-select source on unless testing a fixed amiga_workspace/main.s.
  6. Enable Allow include files only when you intentionally want headers/include fragments in the candidate pool.
  7. Enable Allow non-entrypoint files only when you want to test fragments that may not behave like standalone programs.
  8. When auto-select is on, the server uses manifest_runnable.tsv (strict verify-ready sources).
  9. Click Queue Run Batch.
  10. Watch Live Run Log and Score Trend.
  11. If needed, click Clear Waiting Queue (does not stop an already running job).

12. Create Benchmark Families

When you want to add a new benchmarked effect, do not copy an older benchmark folder by hand. Use the scaffold tool to generate the repetitive structure first, then fill in the task-specific parts.

Run:

python3 tools/new_amiga_benchmark.py "My New Benchmark"

This generates:

  • Reference, control, and mutation workspaces: so the benchmark has a passing source, a failing source, and a mutable source from the start.
  • Frame configs and suite configs: so the evaluator layout is consistent with the rest of the project.
  • Golden image placeholders and a README: so the folder is complete even before the real captures exist.

What you still need to do manually:

  • replace the placeholder assembly with real task code
  • capture real golden images
  • set the correct crop rectangle and timing
  • choose a meaningful pass threshold

The scaffold tool automates the template work. It does not design the benchmark for you.

13. Troubleshooting

  • If the page says refresh failed, confirm the server is still running in Terminal.
  • If run control is unauthorized, open the UI with the correct ?token=....
  • If many runs show `crash`, inspect `build/amiga/report.json` and logs in `build/amiga/`.
