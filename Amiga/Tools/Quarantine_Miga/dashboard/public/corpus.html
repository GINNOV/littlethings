Miga Corpus Guide

This page explains what lives inside amiga_workspace/corpus/, how entries move from raw source trees into the runnable pool, and what the dashboard is actually selecting from during corpus validation runs.

1. What The Corpus Is

The corpus is the project's candidate source pool for normal validation runs. It is not one hand-made program. It is a staged collection of Amiga assembly-like material gathered from upstream trees, filtered into likely source files, then indexed into manifests that the selector and dashboard can use.

  • Raw source trees: original imported material, preserved as source input.
  • Curated files: filtered assembly-like files copied out of the raw trees.
  • Manifest rows: index records describing curated candidates.
  • Runnable manifest rows: the strict subset that assemble and exit cleanly in verification.

2. Corpus Layout

amiga_workspace/corpus/
|- raw/
|- curated/
|- manifest.tsv
|- manifest_runnable.tsv
|- manifest_runnable_report.json
\- scripts/
  • raw/: original source trees, including nested repositories or upstream folder structures.
  • curated/: extracted assembly-like files that passed the indexing filter.
  • manifest.tsv: the broad candidate index built from curated files.
  • manifest_runnable.tsv: the strict run-ready pool used by default when available.
  • scripts/: corpus maintenance and selection helpers.

3. How Entries Move Through The Pipeline

  1. Source trees are stored in amiga_workspace/corpus/raw/.
  2. The indexer copies likely assembly-like files into curated/.
  3. The project writes manifest.tsv as the general candidate index.
  4. The runnable-manifest builder tests those candidates by assembly and verification.
  5. Passing rows are written to manifest_runnable.tsv.

That means the full corpus is wider than the runnable pool. The dashboard usually selects from the strict runnable subset, not from every imported file.

4. What The Dashboard Actually Uses

During Corpus validation, the selector uses manifest_runnable.tsv by default if that file exists and has real rows. If the runnable manifest is missing or empty, selection falls back to manifest.tsv.

  • Source Filter narrows matching paths inside the chosen manifest.
  • Manifest Index pins one exact manifest row.
  • Seed changes deterministic selection when picking from multiple candidates.
  • Allow include files and Allow non-entrypoint files widen what kinds of entries can be selected.

The selected entry is copied into amiga_workspace/main.s, and the selection metadata is written to build/amiga/selected_source.json.

5. Runnable Means Strict

The runnable manifest is not just a filename list. It is the subset of candidates that survive the project's strict validation gate.

  1. vasmm68k_mot assemble step must succeed.
  2. vamos verification step must exit with code 0.

If manifest_runnable.tsv contains only the header row, the current corpus has no strict verify-clean candidates yet.

6. Maintenance Commands

These are the main commands used to maintain or inspect the corpus pipeline.

python3 amiga_workspace/corpus/scripts/index_raw_sources.py --refresh
python3 amiga_workspace/corpus/scripts/build_runnable_manifest.py
python3 amiga_workspace/corpus/scripts/select_source.py --contains "bootblock"
python3 amiga_workspace/corpus/scripts/select_source.py --index 42
amiga_workspace/corpus/scripts/pick_for_run.sh --seed 1
  • Index raw sources: rebuilds the curated pool and broad manifest from raw inputs.
  • Build runnable manifest: refreshes the strict verify-clean pool.
  • Select source: copies one entry into the active workspace file.
  • Pick for run: helper that builds the manifest if needed, then selects one entry.

7. What The Corpus Is Not

  • It is not the Copper benchmark workspace. That lives under amiga_workspace/benchmarks/.
  • It is not the mutation loop history. That lives in build/amiga/mutation_loop/.
  • It is not the default single editable seed alone. That file is amiga_workspace/main.s.

In short: the corpus is the source pool for validation selection, while the benchmark and mutation paths are separate fixed workflows.
