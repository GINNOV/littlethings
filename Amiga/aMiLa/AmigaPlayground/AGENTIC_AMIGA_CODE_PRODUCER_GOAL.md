# Agentic Amiga Code Producer Goal

## Objective

Build Amiga Playground into a model-assisted Amiga code producer that can create a coherent program, preserve its structure across same-conversation follow-ups, and verify the result with compiler, semantic, and runtime-oriented gates.

The target behavior is not ad hoc snippet generation. A prompt such as "generate two buttons, play and stop of a mod file" should create a structured program model. A later prompt such as "add a third button called Volume Up" should patch that model and source without losing existing controls, routines, state, hardware setup, or compileability. The same discipline applies beyond UI controls: a double-buffered bitplane prompt should produce a structured effect model, and follow-ups such as "set front color to red" should update model state and source state together.

## Program Contract

- Generated source embeds an `AmigaProgramModel` region that records controls, routines, state variables, hardware dependencies, and verification expectations.
- The embedded `AmigaProgramModel` region must contain only canonical commented JSON payload between its begin and end markers. Non-comment text, non-canonical formatting, or unknown JSON keys inside the model region are invalid because the decoder can ignore content while the source still carries hidden model-adjacent payload.
- Embedded model ids and model entry identities must be non-blank and trimmed to canonical values. Controls must have stable IDs, visible labels, and action routines; routines must have IDs and labels; state variables must have IDs and symbols. Imported or hand-edited source with blank or whitespace-drifted model identity is invalid even if the surrounding assembly still contains plausible markers.
- Embedded model ids must be canonical kebab-case, model control/routine/state ids must be canonical snake-case, and model action/routine/state symbols must be valid assembler labels. Visible control labels remain free-form, but internal identities must be safe as patcher keys, marker ids, and source labels.
- Embedded model controls must have unique stable IDs, visible labels, and action routines. Imported or hand-edited source with duplicate model control identity is invalid even if the surrounding assembly still contains plausible markers.
- Direct structured add-control mutation entry points must trim visible labels before deriving stable IDs, model markers, label data, and verification expectations, and must reject blank labels before source mutation. Planner-level trimming is not enough if direct patcher callers can bypass it.
- Direct structured rename mutation entry points must trim current and replacement labels before lookup, model marker replacement, chip label-data replacement, and verification expectations, and must reject blank replacement labels before source mutation. Planner-level trimming is not enough if direct patcher callers can bypass it.
- Embedded model control labels must not contain line breaks or control characters. Visible labels can contain punctuation, quotes, and backslashes, but they must remain representable as one-line model markers and assembler label-data directives.
- Every control action must be declared as a model routine with the same stable control ID and action label. A source label in the routines region is not enough if the embedded model no longer tracks that action routine as part of the control contract.
- A model with bounded UI controls must declare the full support routine pipeline in the embedded model: `DrawControls`, `DrawControlRect`, `DrawControlLabel`, `WaitVBlank`, `ReadMouseControls`, `HitTestControls`, and `InputDispatch`, each with its canonical stable routine ID. Source labels alone are not enough because follow-up preservation depends on the model routine payload.
- A model with bounded UI controls must declare the full UI state pipeline in the embedded model: `SelectedControl`, `ActivatedControl`, mouse coordinates, raw mouse counters, button state, previous button state, and click-edge state, each with canonical stable state IDs and expected initial values. Source labels alone are not enough because follow-up preservation depends on the model state payload.
- Embedded model controls with bounds must have positive dimensions, remain inside the 320x256 UI surface, and not overlap another bounded control. Internally consistent markers are not enough if the modeled control geometry is impossible or ambiguous to draw or click.
- Embedded model routines and state variables must also have unique identities. Duplicate routine IDs, routine labels, state IDs, or state symbols are invalid because follow-up patches use those identities to preserve behavior and update scoped state.
- Embedded routine and state-variable purposes must be non-blank and trimmed. Purpose metadata is preserved across follow-ups and is part of the semantic contract, not disposable prose.
- Embedded routine and state-variable purposes must not contain line breaks or control characters. Structured metadata can be descriptive, but it must remain one-line canonical payload so preservation diagnostics and model/source audits cannot be split or hidden.
- Embedded routine clobber and call metadata, when declared, must contain non-blank, trimmed, non-duplicate entries with no line breaks or control characters. Duplicate detection is case-insensitive because routine metadata names executable labels and registers. Routine payload metadata is preserved across follow-ups, so low-quality entries are invalid before they can become false preservation evidence.
- Embedded routine call metadata, when declared, must name real labels and match actual `bra`/`bsr`/`jsr` control-flow edges in the routine body. A model-backed source cannot claim a call graph edge that the executable source does not contain.
- Routine call graph checks must recognize sized direct control-flow forms such as `bsr.w`, `bsr.l`, and `jsr.l` as real named routine edges, while indirect calls such as `jsr (a0)` must not satisfy named call metadata.
- Embedded routine call metadata must be complete for calls to other modeled routines. A routine body cannot call another model routine while omitting that edge from its own `calls` payload, because follow-up preservation depends on the model carrying the real internal program graph.
- Bounded UI support routines must declare their required call graph in the model. `DrawControls` must declare `DrawControlRect`, `DrawControlRect` must declare `DrawControlLabel`, and `InputDispatch` must declare every modeled control action it dispatches. Adding a supported control must intentionally expand `InputDispatch` call metadata with the new action.
- Double-buffered bitplane routines must declare their shared copy call graph in the model. `DrawBufferA` and `DrawBufferB` must both declare `CopyPattern`, and the executable source must contain matching control-flow edges instead of relying on implicit fallthrough that follow-up edits can accidentally break.
- Double-buffered `CopyPattern` verification must prove the hidden-buffer copy loop semantically: executable `move.l (a1)+,(a0)+`, counted `dbf d0,.copy` with valid size/case variants, and `rts`. Swapped copy direction, wrong loop registers, wrong loop targets, or comment-only text must not prove the copy routine.
- Double-buffered bitplane pointer-swap evidence must use direct subroutine-call semantics for `WaitVBlank`, `DrawBufferB`, and `DrawBufferA`. Sized direct `bsr`/`jsr` forms are valid, while indirect calls cannot prove vblank pacing or hidden-buffer drawing.
- Embedded routine clobber metadata, when declared, must use supported 68000 data/address register names or ranges and must match actual register writes in the routine body. A model-backed source cannot claim a clobber that the executable source does not perform.
- Routine clobber checks must recognize common direct register writes including quick/immediate arithmetic and `movem` register-list destinations, while `movem` register-list saves to memory must not satisfy clobber metadata.
- Embedded state initial values, when declared, must be non-blank and trimmed. State payload metadata must not carry whitespace drift that can hide model/source mismatches during follow-up edits.
- Embedded state initial values, when declared, must not contain line breaks or control characters. State values are compared against single source operands and must remain one-line model facts.
- Embedded state initial values, when declared, must have a parseable single-operand `dc.w` declaration inside the closed state region, and the source word value must match the model. A present label with an unparsable directive or extra word operands is not valid state evidence.
- Model-to-source state initial value checks should compare parseable word literals semantically, so equivalent decimal, `$` hexadecimal, and `0x` hexadecimal values are valid while malformed state literals still fail closed.
- Embedded hardware dependencies must be unique. Duplicate hardware entries are invalid because they inflate apparent capability coverage without adding executable behavior.
- Embedded hardware dependencies must have executable source proof for the declared subsystem. A model-backed source cannot claim Paula, CIA, bitplane, Copper, sprite, blitter, or Exec capability unless executable instructions, or intentional scoped bitplane data labels, carry the corresponding hardware evidence.
- Executable source must not use major hardware subsystems absent from the embedded model. Source proof for Paula, CIA, bitplanes, Copper, sprites, blitter, or Exec is invalid unless the model declares the matching hardware dependency, and register-looking text inside data directives is not hardware proof.
- Embedded model verification expectations must be non-blank, trimmed, and unique under case-insensitive comparison. They are behavioral obligations for follow-up preservation, not decorative notes or duplicate coverage padding.
- Embedded model verification expectations must not contain line breaks or control characters, because expectations drive preservation and supersession diagnostics across follow-ups.
- Known embedded model verification expectation families must match model facts and executable source evidence. Control dispatch expectations must either name a current control and its modeled action or, after a label rename, still resolve to an existing modeled control action; state-backed expectations such as initial volume and front/back bitplane colors must match model state values; volume-step expectations must be backed by an existing volume routine using semantic `add.w`/`sub.w` immediate evidence for that step; and playback-state preservation expectations must require modeled playback state plus semantic executable Play/Stop writes that set and clear it.
- Each supported structured program family has an `AmigaProgramFamilyManifest` entry that declares accepted and rejected first-shot prompts, supported follow-ups, required follow-up smoke prompts, required rejected follow-up smoke prompts, required rejected follow-up smoke chains, required regions, hardware dependencies, and promotion gates. Manifest identity and coverage declarations must be non-blank, trimmed to canonical values, and unique within their lists, and accepted and rejected first-shot examples must not overlap.
- A source using a registered family id must also use that family's registered model kind. Family id alone is not enough to claim an audio player, effect, or demo contract, because follow-up patchers and semantic preservation gates depend on the model kind as part of the source identity.
- The family registry is promotion-audited. A registered family must provide a verified source provider, route its first-shot prompt examples back to the same family id, declare the baseline verification gates, pass source and semantic verification, compile its verified first-shot source and every routed first-shot prompt example, successfully apply compileable required follow-up smoke prompts from both the verified source and every routed first-shot source without losing earlier controls or routines, and reject declared unsupported follow-ups through the structured planner rather than ignoring them or patching them.
- Supported follow-up declarations are canonical audited capability names scoped to the active program family. A manifest cannot claim arbitrary or cross-family follow-up support unless that capability is backed by the family-specific structured planner, smoke coverage, and preservation audit.
- Structured follow-up planners and patcher mutation entry points must gate supported edits by the active embedded model family id. A valid but unregistered or future model-backed family must not accidentally inherit MOD controls, bitplane color edits, or another family's patch capabilities.
- Structured patcher mutation entry points must also fail closed on unsupported enumerated values such as bitplane colors. Planner-level rejection is not enough if a direct patcher call can silently fall back to a default value and return a verified but unintended source edit.
- Direct structured bitplane color mutation entry points must trim and canonicalize color roles and color names before state lookup, model updates, source replacement, and verification expectations. Planner-level canonicalization is not enough if direct patcher callers can bypass it.
- Verification gate declarations are canonical audited deliverables. A manifest cannot satisfy the promotion contract with case-mutated, misspelled, or unsupported gate names that are not backed by the audit.
- Registered family IDs and names must be unique, and accepted first-shot prompt examples must not overlap across families. The registry must not be empty and must not contain identity collisions or ambiguous first-shot ownership.
- Required conversation smoke chains must contain at least two follow-ups and must not repeat prompts or duplicate another declared chain. A one-step smoke chain is only an isolated patch check; it does not prove same-conversation continuity.
- Every declared supported follow-up category must have accepted smoke coverage. A manifest cannot claim support for a behavior that is only listed in prose and never exercised by required accepted smoke prompts, accepted smoke chains, or accepted setup prompts inside rejected follow-up smoke chains.
- Accepted smoke prompts must map back to declared supported follow-up categories. A manifest cannot exercise extra accepted behavior in smoke tests while leaving that capability absent from its advertised support surface.
- Editable source is divided into named regions for model data, controls, drawing, hit testing, dispatch, routines, state, and chip data.
- Required model-backed source regions must each have exactly one begin marker and one end marker. Duplicate or missing boundaries are invalid because the verifier and patcher must not depend on overwritten or ambiguous region slices.
- Required model-backed source regions must appear in canonical non-overlapping order. A region end before its begin, or a required region that starts before the previous required region closes, is invalid because region ownership must be deterministic for model patching and preservation audits.
- Source region markers and structured patch `changedRegions` declarations must use canonical region names only. Unknown region names or marker actions are invalid because the producer must not create new ownership surfaces outside the audited model-backed contract.
- First-shot model-backed templates must pass `AmigaProgramSourceVerifier` before prompt routing can return them to the UI. A stale or internally inconsistent template must fail closed before it becomes editor content.
- First-shot structured family recognition must match prompt concepts as complete tokens or phrases, not substrings. For example, a prompt containing `display`, `stopwatch`, and `modulator` must not route to the MOD play/stop controls family merely because those words contain `play`, `stop`, and `mod`.
- First-shot structured family recognition must also require the family-specific domain concepts. For example, a generic double-buffered audio request must not route to the double-buffered bitplane family unless the prompt also asks for bitplanes and pointer-swap/animation behavior.
- Follow-up edits operate on the model and marked regions first. Free-form LLM editing is a fallback, not the primary mechanism for supported program families.
- Structured follow-up edits must verify the current model-backed source before applying a patch. A patch must not silently repair, normalize, or overwrite an already invalid model contract as a side effect of a requested edit.
- UI controls keep focus state separate from one-frame action state. `SelectedControl` describes focus; `ActivatedControl` is set by click-edge hit testing, consumed by `InputDispatch`, then cleared.
- Every control must have a visible draw path, hit-test path, dispatch marker, executable action routine, rectangle data, and label data.
- Control action routines must live inside the closed `routines` region and must not collapse to a bare no-op return.
- Model-declared support routines must live inside their expected regions: drawing routines in `draw_controls`, input and hit-test routines in `hit_test`, dispatch in `input_dispatch`, and action routines in `routines`.
- Mouse input invariants must be scoped to the expected routines: hardware reads, delta state updates, click-edge updates, and coordinate clamps belong in `ReadMouseControls`, while click-edge consumption belongs in `HitTestControls`.
- Each control dispatch block must compare the activated control value against that control's model slot before calling the action routine.
- Each control dispatch block must be guarded by its own skip label: compare activated slot, branch away on mismatch, call the action routine, then land at that control's skip label. A compare and action call in the same area is not enough.
- Control dispatch checks must use the same direct routine-call semantics as routine call graph checks: sized direct calls such as `bsr.w StopMOD` are valid dispatch evidence, while indirect calls such as `jsr (a0)` are not proof that the modeled action routine executes.
- Guard, loop, and copy-path branch checks must recognize direct sized branch forms such as `bne.w .skip_stop`, `blt.w .miss_stop`, `bra.s .doneHitTest`, and `bra.w CopyPattern`, while still requiring the expected branch mnemonic and direct target.
- Follow-up promotion checks must preserve existing routine payload, not only routine identity. A patch may add new routines for new supported behavior, but it must not silently alter the purpose, clobbers, or call metadata of routines that already existed.
- Follow-up promotion checks must preserve existing action routine source bodies unless a supported parameter edit explicitly supersedes that action body, such as changing the volume step inside `VolumeUp` or `VolumeDown`. An unrelated follow-up must not rewrite `PlayMOD`, `StopMOD`, or another existing action while keeping the model metadata intact.
- Supported parameter edits must patch accepted assembler numeric styles in existing source, including decimal, `$` hexadecimal, and `0x` hexadecimal immediates, so a verifier-clean prior follow-up cannot become uneditable merely because its operands are formatted differently.
- Follow-up promotion checks must also preserve model-declared support routine source bodies, such as `WaitVBlank`, `ReadMouseControls`, `DrawControlRect`, and `DrawControlLabel`. Adding controls may expand the control pipeline routines that own control lists, hit-test branches, and dispatch branches, but unrelated follow-ups must not silently rewrite preserved support code.
- Follow-up promotion checks must preserve existing labeled `chip_data` blocks. A label rename may update the matching `ControlLabel_*` data block, and adding a control may add new rectangle/label blocks, but unrelated data such as samples, buffers, patterns, and existing rectangles must not silently drift.
- Model-backed follow-ups must not create unsupported no-op controls. If a requested control's behavior is not implemented by the active program family, the planner should reject the patch with a concrete explanation instead of generating a routine that merely returns or falling through to free-form source editing.
- Direct structured add-control mutation entry points must also reject unsupported control behavior instead of creating fallback no-op action routines. Planner-level unsupported-control rejection is not enough if direct patcher callers can bypass it.
- Existing non-conflicting behavior must survive chained follow-ups.
- Follow-up promotion checks must preserve existing hardware dependencies and reject newly added hardware dependencies unless they are declared by the active program family's manifest.
- Non-conflicting follow-ups include adding controls, adjusting supported parameters, and renaming visible control labels without changing the control identity, model slot/order, bounds, action routine, dispatch slot, or preserved state.
- Follow-up promotion checks must preserve existing control labels unless a structured rename explicitly supersedes the label while keeping the same control identity and action routine. Unrelated follow-ups must not silently relabel existing buttons.
- Verification expectations embedded in the model must survive non-conflicting follow-ups. A follow-up may supersede a known parameter expectation family, such as volume or front/back buffer color, but it must not silently drop earlier behavioral obligations like play/stop dispatch, pointer-swap pacing, clean exit, or playback-state preservation.
- Supersession must be prompt-aware. A patched model cannot authorize a rename, volume-step change, initial-volume change, or front/back color change merely by adding the right verification expectation; the user prompt must also match that supported follow-up category.
- Add-control follow-ups should keep visible labels separate from implemented behavior. A request such as "add a third button called Louder to raise volume" should create a control labeled `Louder` that dispatches to the supported `VolumeUp` action, not discard the requested label or create unsupported behavior. Canonical supported labels such as `Louder`, `Quieter`, `Pause`, or `Mute` may imply the matching supported action even when the prompt does not repeat behavior words. The planner should recognize natural label phrasing including quoted text, `called`, `named`, `label`, `text`, `caption`, and `title`.
- Supported add-control behavior words and canonical labels must match as complete tokens, not substrings. For example, "add another button called Louderness" should reject as unsupported instead of silently creating a `VolumeUp` control.
- Add-control behavior detection must distinguish requested behavior from incidental words in the prompt. If a user asks for a `Louder` button "after I stop and play the mod", the requested behavior is still `VolumeUp`; incidental existing-control words must not create a false multi-behavior conflict.
- Add-control follow-ups with conflicting behavior signals must reject instead of guessing. A request such as "add a third button called Mute to pause the mod" names two supported behaviors and should ask for exactly one behavior rather than silently choosing one.
- Multi-control add follow-ups with canonical supported behaviors must add every unambiguous requested control or reject. For example, "add volume controls", "add volume up and volume down", and "add a volume up button and a volume down button" should create both controls and must not silently add only `Volume Up`. When the user names multiple controls explicitly, the model, dispatch table, and drawn layout must preserve the prompt order, such as adding `Volume Down` before `Volume Up` for "add volume down and volume up".
- Repeated controls in the same add-control follow-up must reject instead of collapsing to a single patch. A request such as "add volume up and volume up" or "add a mute button and a mute button" is ambiguous duplicate intent, not permission to silently add one control.
- Duplicate supported behavior should reject at the model level with a user-facing diagnostic. If `Louder` already dispatches to `VolumeUp`, a later "add volume up" should report that the behavior already exists through `Louder`, not leak an assembler routine-label collision.
- Duplicate visible labels should reject at the model level even when the requested behavior is different. If `Play` has been renamed to `Start`, a later request to add a volume control also called `Start` should fail instead of creating two indistinguishable buttons.
- Follow-up promotion checks must reject newly added model controls unless the prompt is a declared add-control capability for the active family, and must reject newly added routines unless they are the action routine for one of those supported added controls.
- Rename follow-ups must not reintroduce another control's stable identity. If `Play` has been renamed to `Start`, a later request to rename `Stop` to `Play` should reject because the `play` control identity is already owned by the original play control.
- Parameter edits should apply to the compatible behavior already present in the model. For example, changing the volume increment after only `Volume Up` exists should update `VolumeUp` without requiring or inventing `VolumeDown`; the same request before any volume control exists should reject with a concrete missing-capability diagnostic.
- Recognized parameter edits with missing values must fail closed. For example, "change volume step", "set initial volume", "set front color", and incomplete separator forms such as "set front color to" should reject with a concrete missing-value diagnostic instead of falling through to generic source editing or being misreported as unsupported values.
- Numeric parameter edits must parse signed integer values before applying range rules. For example, "set initial volume to -1" should clamp to zero, not accidentally become one, and "change volume step to -8" should clamp to the minimum supported step.
- Numeric parameter edits should accept Amiga-style `$` hexadecimal and C-style `0x` hexadecimal values. For example, "set initial volume to $20" should update model and source state to decimal `32`, not decimal `20`.
- Numeric parameter edits with multiple numbers must select the explicit target value after separators such as `to` or `=` rather than the first incidental number. For example, "change volume step from 4 to 8" should patch step `8`, and "set initial volume to 32 for channel 0" should patch volume `32`.
- Multi-target structured edits must either patch every unambiguous target or reject; they must never silently apply a partial edit. For example, "set front and back color to red" should update both bitplane color states, "set front color to red and back color to blue" should update each named role, and incomplete forms should ask for a clearer request.
- Parameter intent words, edit verbs, and structured follow-up action words such as add, rename, text, title, caption, called, named, and say must match as complete tokens or phrases, not substrings. For example, "set volume amounting to 8" must not be treated as a volume-step edit, "make volume currentness 32" must not be treated as an initial-volume edit, "upset front color to red" must not be treated as a bitplane color edit, "change Stop button texture to Halt" must not be treated as a label edit, and "addendum raise volume" must not be treated as an add-control request.
- Supported enumerated values must match as complete tokens, not substrings. For example, "set front color to greenhouse" must not be accepted as `green`; it should reject as an unsupported front-buffer color.
- State-backed parameter edits should update both embedded model metadata and the scoped source region. For example, setting the initial volume should update the model's `audio_volume.initialValue` and the `AudioVolume` word inside the closed `state` region.
- State-backed parameter patchers must preserve valid assembler declaration shape. A split declaration such as `AudioVolume:` followed by `dc.w 48` should update the following word data, not collapse the label line or leave stale state data behind.
- Routine parameter patchers must accept valid assembler case variants in existing source. A volume-step edit should update `ADD.W #4,D0` and `SUB.W #4,D0` just as reliably as lowercase canonical template lines.
- Volume-step verification expectations must compare arithmetic operands semantically. Equivalent decimal, `$` hexadecimal, and `0x` hexadecimal immediates are valid, but the operation must target `d0` in the modeled volume routine.
- Playback-state verification expectations must compare operands semantically. Equivalent immediate forms for setting `PlaybackState` are valid, but PlayMOD must write `#1` to `PlaybackState` and StopMOD must clear `PlaybackState`, not a different state symbol.
- Structured source verification must accept equivalent assembler numeric forms while still failing closed on malformed operand lists. For example, control rectangle `dc.w` data may use `$` or `0x` hex values, but an unparseable extra operand must not be silently dropped into a false match.
- Word-data operand parsing must fail closed on empty operands as well as unparseable operands. A trailing comma in state or control-rectangle `dc.w` data is malformed and must not be accepted as if the missing operand did not exist.
- Hit-test compare immediates and slot writes must accept equivalent decimal, `$` hexadecimal, and `0x` hexadecimal forms while failing closed on malformed immediates, so clickable bounds and activation slots are verified semantically rather than by brittle text equality.
- Hit-test coordinate loads must compare operands semantically. Equivalent formatting for `MouseX(pc)` and `MouseY(pc)` loads is valid, but guarded activation must load the correct coordinate into `d0` before each bounds comparison.
- Dispatch slot compare immediates must accept equivalent decimal, `$` hexadecimal, and `0x` hexadecimal forms while failing closed on malformed immediates, so the executable action guard can share the same slot semantics as hit testing.
- Double-buffered bitplane verifier checks must compare instruction operands semantically for hardware register writes, bit tests, color writes, buffer pointers, and frame-state immediates. Equivalent case, spacing, `$` hexadecimal, and `0x` hexadecimal forms are valid; malformed immediates are not.
- Double-buffered copy-loop verifier checks must compare instruction operands semantically. Equivalent case and valid `.w` `dbf` sizing are valid; malformed copy direction or loop operands are not.
- State variable verification should enforce model-to-source value fidelity inside the scoped `state` region. A matching label or value elsewhere in the source must not hide drift between the embedded model and the executable state declaration.
- The scoped `state` region must not contain unmodeled state symbols. Every state label in executable source must be declared in the embedded model, so follow-up preservation cannot miss hidden state added outside the model contract.
- Follow-up promotion checks must preserve existing state payload, not only state identity. A patch may intentionally change supported state-backed parameters such as `AudioVolume`, `FrontColor`, or `BackColor`, but unrelated follow-ups must not silently alter a state variable's purpose or initial value.
- Follow-up promotion checks must reject newly added model state variables unless a future family-specific capability explicitly declares and verifies that state growth.
- Hardware dependency verification must use executable operand evidence, not incidental text. Register-looking values in comments, data directives, string literals, or immediate operands must not satisfy a model hardware dependency or create an undeclared one.
- Structured patchers must treat `@amiga:` metadata as metadata only when it appears in semicolon marker comments. Quoted marker-looking text in data directives or other source payload must never be selected as the line to patch.
- Assembly comment parsing must respect quoted string operands. A semicolon inside single- or double-quoted data is payload, not a comment marker, so labels such as `Stop;Now` and quoted marker-looking text cannot be truncated or mistaken for metadata.
- Follow-up planning should accept natural references to existing controls, including visible labels, stable model IDs, quoted labels, label/text/caption/title phrasing, action semantics such as "volume up" for a custom-labeled `VolumeUp` control, and ordinal descriptions such as "the third button" when the model has a corresponding control.
- Quoted follow-up labels must be interpreted in source order even when the prompt mixes straight double quotes, curly quotes, and single quotes. For example, `rename 'Stop' to "Halt"` must treat `Stop` as the current label and `Halt` as the new label, not reorder matches by quote style.
- Existing-control references in unquoted follow-ups must match complete tokens or phrases, not substrings. For example, "change Stopper button text to Halt" should not rename `Stop`; it should reject as ambiguous or unsupported rather than guessing.
- Out-of-range ordinal control references must fail closed. A request such as "rename the fourth button to Louder" on a two-control model should reject with the actual control count instead of falling through to generic source editing or reporting a vague ambiguity.
- Add-control ordinal requests must match the next model slot. A request such as "add a fourth button called Louder" on a two-control model should reject because the next valid slot is the third control.
- Ambiguous follow-up references must fail closed. A request such as "rename the button to Halt" on a multi-control program should reject with a concrete list of candidate controls rather than guessing or falling through to generic source editing.
- Production follow-up planning must fail closed: after a structured patch, the resulting source must pass `AmigaProgramSourceVerifier` before it can be returned to the UI.
- Production follow-up planning must also fail closed before patching when the current model-backed source already fails `AmigaProgramSourceVerifier`. Preflight failure is a rejection, not an opportunity for the patcher to normalize the broken source while performing an unrelated edit.
- Structured patcher mutation entry points must enforce the same current-source preflight after family gating and before request-specific mutation. Direct calls to add controls, rename labels, change volume parameters, or change bitplane colors must not mutate an already-invalid structured source or let unrelated request diagnostics hide the existing model/source failure.
- Structured patcher mutation entry points must verify their patched output before returning it. Planner-level post-verification is not enough if direct patcher callers can receive a source that violates the embedded model contract.
- Recognized structured follow-up rejections must also preflight the current model-backed source. Missing values, unsupported enum values, ambiguity, duplicate controls, and ordinal errors should not mask an already-invalid embedded model or source contract.
- A required accepted follow-up must be effective: it must change the source and declare the changed regions truthfully. Returning `.patched` with identical source is a promotion failure, even if the unchanged source still verifies.
- Structured follow-up patches must not change source outside closed model-backed regions. If a future capability needs to alter executable setup or teardown text, that text must first become part of an explicit modeled region and promotion contract.
- Assistant prompt routing must give model-backed follow-ups first refusal before generic source editing. A rejected structured patch is terminal for that request: the UI must keep the editor unchanged and report the structured failure instead of asking the LLM to free-form edit the source.
- Required rejected follow-up smoke prompts are part of the promotion surface. They must be recognized by the structured planner and rejected with concrete reasons; an unrecognized prompt is a coverage gap, and an accepted patch is a contract violation.
- Rejected follow-up smoke prompts must still exercise the family's declared structured follow-up surface. Negative prompts may test malformed values, unsupported controls, duplicates, or ambiguity, but they must not smuggle unrelated capabilities such as arbitrary background edits into the manifest.
- Required rejected follow-up smoke chains prove fail-closed behavior after accepted edits. Setup prompts in those chains must pass the same effect, model, region, preservation, verifier, and semantic checks as accepted smoke prompts, then the final prompt must reject on the patched source. Rejected-chain declarations must not duplicate another declared chain, and setup prompts inside a rejected chain must not repeat; the final rejected prompt may intentionally repeat a setup prompt when proving duplicate-follow-up rejection.
- Compile promotion must include routed first-shot follow-up artifacts, not only the verified source provider. A parameterized accepted first-shot prompt must embed the expected family model id and kind, then produce compilable output after every required accepted smoke prompt, smoke chain step, and rejected-chain setup step.
- Accepted follow-up smoke artifacts used as compile evidence must first pass effect, changed-region truthfulness, model/source identity, preservation, `AmigaProgramSourceVerifier`, and semantic invariant checks. Compile success is not enough if the artifact is a no-op, under-declares regions, over-declares regions, changes text outside modeled regions, returns a model that drifts from the embedded source contract, silently changes prior model/routine/data payloads, or violates family-specific semantics such as Paula audio setup or bitplane pointer swapping.
- The UI must not fall back to free-form model editing when a recognized model-backed follow-up cannot be verified. It should leave the editor unchanged and report the concrete verification or patching failures.
- Structured patch rejection messaging must match the actual failure class. Unsupported controls, ambiguity, missing values, duplicate requests, and verifier failures are all terminal structured outcomes, but only real verifier failures should be described as verification failures in user-facing text.
- Reliability-gate failure on source with an embedded `AmigaProgramModel` must fail closed. The app must not ask the LLM to free-form repair a structured source after compiler or semantic failure, because that can silently discard the model contract.
- UI loop pacing invariants must be scoped to the executable entry loop and `WaitVBlank` routine. Matching `WaitVBlank`, VPOSR, or `.mainLoop` branch text elsewhere in the source must not satisfy the verifier.
- UI entry-loop invariants must prove the executable wiring, not just routine presence: `_Start` draws controls before polling, and `.mainLoop` reads mouse input, hit-tests controls, and dispatches actions in that order.
- UI entry-loop and polling-pipeline checks must accept sized direct `bsr`/`jsr` subroutine-call forms such as `bsr.w WaitVBlank` and `jsr.l DrawControls`, while indirect calls such as `jsr (a0)` must not satisfy executable wiring evidence.
- Mouse click-edge, raw-counter, clamp, hit-test selection/activation, and dispatch activation-state checks must be executable normalized instruction evidence inside the expected routines. Spacing and case variants are valid, but comment-only instruction text must not prove UI input, hit-test state writes, or dispatch state updates.
- Mouse click-edge, raw-counter, hit-test click source, and dispatch activation-state checks must compare instruction operands semantically. A matching mnemonic with the wrong source register, state symbol, destination, or clear target must fail even if the surrounding routine still looks plausible.
- UI input and drawing verifier checks must compare numeric operands semantically for hardware register reads, CIA button tests, row stride setup, edge-pixel writes, and pointer clamps. Equivalent decimal, `$` hexadecimal, and `0x` hexadecimal forms are valid; malformed operands must fail closed.
- Mouse hardware reads and vblank hardware reads must be executable instruction evidence inside the expected routines. Comment-only `$0a(a6)`, `$bfe001`, or `$06(a6)` text must not prove JOY0DAT input, CIA mouse-button input, or vblank pacing.
- Verifier checks for dispatch behavior must be scoped to the executable `input_dispatch` region before its return, not satisfied by matching text elsewhere in the source.
- State variables declared by the embedded model must live inside a closed `state` region. A same-named label elsewhere in the source is not enough.
- Control, draw, hit-test, and dispatch markers must be found inside their declared regions. Marker text outside the expected region must not satisfy the verifier.
- Control markers must match the embedded model's id, label, action, and bounds, so the controls region cannot drift from the structured source of truth.
- Control marker label attributes must escape marker syntax characters such as quotes and backslashes while preserving the model's visible label. The chip-data `dc.b` string must independently use valid assembler string escaping, so a label such as `Bass "Boost"` remains patchable and verifiable in both metadata and executable data.
- Control, draw, hit-test, and dispatch marker IDs must be owned by embedded model controls. Extra markers for unmodeled controls are invalid because they imply UI behavior that follow-up planning and preservation cannot see.
- Control, draw, hit-test, and dispatch marker IDs must be unique within their pipeline regions. Duplicate markers for the same modeled control are invalid because follow-up patching must not depend on whichever marker the verifier happens to find first.
- Control rectangle and label data must live inside the closed `chip_data` region. `ControlLabel_*` data must match the embedded model's control label text, accepting equivalent directive spacing/case and valid quote style while preserving exact label text, so the drawn UI cannot drift from the model during follow-up edits.
- `ControlRect_*` data must match the embedded model bounds and control slot, so drawn geometry cannot drift from the model during follow-up edits.
- Known structured families must not carry unmodeled chip-data labels. MOD controls may use model-derived control rectangle/label blocks plus declared support data such as `BitplaneBuffer` and `Sample`; double-buffered bitplanes may use `BufferA`, `BufferB`, `PatternA`, and `PatternB`. Extra labels inside `chip_data` are invalid until the model contract grows to describe them.
- Draw-control markers must match the embedded model's slot and bounds, and each draw path must use executable PC-relative `lea ControlRect_*(pc),a0` evidence for that control's own rectangle data before rendering. Comment-only or unrelated text references are not proof.
- Control drawing invariants must be scoped to `DrawControlRect`. Buffer-target, row-stride, and pixel-write checks must use executable normalized instruction evidence, and matching text elsewhere or in comments must not satisfy the verifier.
- Control label drawing must use direct subroutine-call evidence inside `DrawControlRect`; sized direct `bsr`/`jsr` forms are valid, while indirect calls cannot prove that labels render.
- Hit-test markers and compare instructions must match the embedded model bounds and slot, so clickable geometry cannot drift from drawn and modeled geometry.
- Each hit-test block must be guarded by its own miss label: compare mouse X/Y against all model bounds, branch to `.miss_<id>` on each miss, select and activate the slot only after all bounds pass, then branch to `.doneHitTest`.
- Executable routine labels inside scoped draw, hit-test, dispatch, and action-routine regions must be declared by the embedded model. Extra hidden routine labels are invalid because follow-up preservation cannot track behavior that only exists in source.
- Action routine body checks must require a real executable instruction beyond `rts`; assembler data/directive lines such as `dc.w` must not prove that a modeled control action has behavior.
- Scoped label ownership checks must treat concrete assembler labels consistently whether they start at column zero or are indented, while ignoring labels that only appear in comments or quoted data. Hidden indented helpers are still hidden behavior and must be rejected unless modeled.
- State, routine, chip-data, preservation, and region-ownership checks must use the shared source-index label parser rather than independent raw-prefix label tests, so all model/source proof gates agree on which labels are concrete assembler symbols.
- UI entry-loop scans must use the shared concrete-label parser for `_Start` and `.mainLoop`, so indented assembler labels are accepted while comment-only label text remains ignored.
- Double-buffered bitplane entry/path scans must use the shared concrete-label parser for `_Start`, `.main`, `.showA`, and `.showB`, so indented assembler labels are accepted while comment-only label text remains ignored.
- Return-boundary checks must normalize executable `rts` instructions, accepting comment-suffixed forms such as `rts ; done` while still rejecting markers that appear after the return.
- Structured follow-up insertion points must normalize executable `rts` instructions too, so edits are inserted before comment-suffixed returns instead of appending unreachable behavior after them.
- Structured follow-up label lookups must use the shared concrete-label parser, so valid assembler labels with comments or indentation remain editable while comment-only label text is ignored.
- Model/source marker evidence must come from trimmed `; @amiga:` comment markers only; quoted data text or incidental executable text containing marker substrings must not prove, duplicate, or introduce markers.
- State initial-value verification must accept valid single-operand `dc.w` declarations both on the label line and on nearby data lines after the concrete state label.

## Promotion Bar

A supported program family is promotable only when:

- first-shot generation routes to a structured template or model-backed generator,
- `AmigaProgramFamilyPromotionAudit.failuresForAllFamilies()` returns no failures,
- all supported follow-ups preserve the embedded model and marked regions,
- required accepted follow-ups make real source changes and truthfully declare changed regions,
- required rejected follow-ups and rejected follow-up chains are recognized by the structured planner and reject with concrete diagnostics,
- generated and patched source compiles with VASM,
- `AmigaProgramSourceVerifier` returns no failures,
- `AssemblySemanticValidator` returns no model invariant failures,
- negative tests prove the verifier catches the most likely regressions,
- runtime smoke checks exist for visual or hardware behavior when practical.

## Expansion Path

When adding a new Amiga program family, implement it in this order:

1. Define the model fields and source regions the family needs.
2. Add an `AmigaProgramFamilyManifest` entry that declares prompts, supported follow-ups, required follow-up smoke prompts, required rejected follow-up smoke prompts, required rejected follow-up smoke chains, required regions, hardware, and gates.
3. Add the base template or deterministic generator.
